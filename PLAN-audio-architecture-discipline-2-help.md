# PLAN: Audio Architecture Discipline Part 2 — The Help Page: `jam_tui` and `jam::TerminalPage`

**RFC:** `RFC-message-loop-model.md`. Canon: `PLAN-audio-architecture-discipline-0-tracker.md`, ruling 12.

**Language Constraints:** C++17 / JUCE 8.0.17 / JAM (LANGUAGE.md, C++ / JUCE)

## Overview

cast, ggwp, and scout each hold the same help printer, `printHelp`: 35 lines that differ in one name (`Help.cpp:19`).
This part moves that printer into one JAM module, `jam_tui`, as `jam::TerminalPage`. The three tools then use the module, and whatdbg prints its help through it.
This part also gives whatdbg the module rows that the help page needs. They hold the rows that `jam::Model` needs in Part 6.

## What this part does not do

- No change of the DAP path of whatdbg. The loop, `debug::State`, and each handler stay.
- No change of the text of a `HELP.md` of cast, ggwp, or scout.
- No banner for whatdbg. whatdbg prints no banner today (`Main.cpp:296-300`).

## Language / Framework Constraints

- Ruling 12: `jam::TerminalPage` is a `juce::Component`. "the native juce contract API must holds, no poking terminal at all. this is just juce::Component that uses Terminal graphics as its LLGC".
- `jam::TerminalGraphicsContext` "lets ordinary JUCE painting code … target a terminal cell grid" (`jam_TerminalGraphicsContext.h:5-8`).
- CODING.md, Header discipline: a submodule `.h` and `.cpp` hold no include. Each include is in the module header.
- CODING.md: one object, one translation unit; templates stay in the header.
- `jam_gui` depends on `jam_terminal` (`jam_gui.h:10-18`), and the page needs `jam::TextEditor` of `jam_gui`. So the page is not in `jam_terminal`. It is in the new module `jam_tui`.
- `CMakeLists.txt` and `Source/generated/` are generated by cast. No step edits them by hand.

### `jam::TerminalPage`

`class TerminalPage : public juce::Component`. It is a component that shows one document as text. A caller lays it out and paints it by the JUCE contract. It holds no terminal state and writes no escape byte itself: the terminal graphics context is its low-level graphics context.

Public:
- `TerminalPage (ResourceFetchers fetchers, const jam::Strings& styleSheets);` It builds `styleManager` from the two arguments. Its body calls `addAndMakeVisible (editor)`, `setLookAndFeel (&styleMarkdown)`, and `setSize (styleMarkdown.getColumnWidth(), 0)`, in this order.
- `~TerminalPage() override;` Its one statement is `setLookAndFeel (nullptr)`. The threat: the member `styleMarkdown` dies before the `juce::Component` base, which still names it as its LookAndFeel.
- `template <typename DocumentType> void setDocument (DocumentType document)`, in the header. Its one statement is `editor.setDocument (std::move (document));`. This is the signature of `jam::TextEditor::setDocument` (`jam_TextEditor.h:196-197`).
- `void resized() override;` Its one statement is `editor.setBounds (getLocalBounds());`. With the size of the constructor, the editor gets the bounds of `Help.cpp:18`.
- `void writeToStream (juce::OutputStream& output);` Its body is `Help.cpp:21-32`, with three changes: `columnWidth` is `getWidth()`; `component` is `editor`; `buffer.writeToStream (frame, styleMarkdown)` is `buffer.writeToStream (output, getLookAndFeel())`. The `jam::TerminalBuffer buffer` of `Help.cpp:9` is a local of this function.

Private members, in the order of `Help.cpp:5-16`:
- `jam::SharedInstance<jam::SharedDocuments> documents { std::in_place };`
- `jam::Typeface typeface;`
- `const jam::GlyphArrangement glyphArrangement;`
- `jam::StyleManager styleManager;`
- `jam::StyleMarkdown styleMarkdown;`
- `jam::TextEditor editor;`
- `JUCE_DECLARE_NON_COPYABLE_WITH_LEAK_DETECTOR (TerminalPage)`

### The call site of each tool

In `printBannerAndHelp`, the one line `printHelp (BinaryData::getString (files::<name>Help));` becomes these five lines:

```
jam::TerminalPage page { { BinaryData::fetcher }, jam::Strings { files::styleSheet } };
```

## BLESSED Alignment

- **B — Bound.** The page owns its style manager, its LookAndFeel, and its editor. The destructor releases the LookAndFeel before the members die.
- **L — Lean.** One class replaces three copies of 35 lines. One style sheet replaces three files of 632 lines.
- **E — Explicit.** The fetchers and the style sheet names are constructor arguments. The page reads no global of a tool.
- **S — SSOT.** `jam::TerminalPage` is the one help printer. `jam_tui/page/style.css` is the one style sheet.
- **S — Stateless.** The terminal buffer lives inside one `writeToStream` call.
- **E — Encapsulation.** Ruling 12. The page is a `juce::Component`; it paints through `juce::Graphics`, and the terminal graphics context is the device. The tool writes the bytes to stdout.
- **D — Deterministic.** The output of each of the three tools is byte-equal before and after (Step 5).
- LANGUAGE.md: no override applies beyond the C++ / JUCE Lean adaptation.

## Risks / Open Questions

None open.

Facts for the review of the whole PLAN:

- **The page paints the viewed component of its editor**, as `printHelp` does (`Help.cpp:28`), not the page itself. A paint of the page clips the editor to the page height, which is 0. This keeps the output byte-equal.
- **The banner lines stay in each tool.** `printBanner` reads `map::banner`, a table that each tool generates (`scout/cast/banner.md`).
- **The help page of whatdbg changes its look.** It is rendered markdown with SGR colour bytes, also when stdout is no terminal (tracker, Facts).
- **The `FILES` section of the whatdbg help names `~/.config/whatdbg/dbgeng/`.** The code uses `userApplicationDataDirectory` (`Main.cpp:108`; Part 1, T8). Step 8 copies the text unchanged.
- **This part changes five repositories**: jam, cast, ggwp, scout, whatdbg.
