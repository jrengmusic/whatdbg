## Context

Every full 10-scenario smoke run left exactly one new unreapable zombie (`PPID=1`), previously
misclassified as a `02_attach` test-harness artifact (`SMOKE-20260902T174913Z.md`). That
classification is wrong. Root-caused with direct process-table evidence: the zombie is
`fixture_crash` (scenario `08_crash`), produced by a genuine whatdbg defect in
`Session::terminateDebuggee`, not by the harness.

## Investigation

**Isolated `02_attach` repro (4 runs, single-scenario nvim script, no other scenarios in the
process):** zombie count identical before/after on every run. `fixture_wait`'s `ps` history
showed it reparented under a `debugserver` child during attach, then vanished cleanly (no `Z`
state ever observed) once `terminate` (which routes to `Session::terminateDebuggee` — a plain
breakpoint/thread-started stop, `Signal(SIGKILL)` succeeds) ran. `02_attach` is exonerated by
direct evidence — it does not leak a zombie in isolation, contradicting the standing assumption.

**Isolated `08_crash` repro (3 runs, pre-fix):** zombie count rose by exactly 1 on every single
run (100% reproduction). `~/Library/whatdbg/whatdbg.log` (JUCE_DEBUG diagnostic log, `Main.cpp`'s
`Log::Scope`) captured the exact failure on every run:

```
[Whatdbg] exception stopped: EXC_BAD_ACCESS 0x1 at 0x10243c668 (threadId=3681241)
[Whatdbg] command=terminate seq=5
[Session_mac] terminateDebuggee failed: failed to send signal 9
[Whatdbg] exception stopped: EXC_BAD_ACCESS 0x1 at 0x10243c668 (threadId=3681241)
```

`fixture_crash`'s `ps` state was observed stuck in `TX`/`SX` (ptrace-stopped) for the entire
process lifetime after the failed `terminate` — the debuggee never advances. `debugserver`
(`fixture_crash`'s real tracer, `ps` confirmed) itself reparented to `launchd` (`PPID=1`) partway
through, meaning `whatdbg`'s own process had already exited while `debugserver` and its
still-ptrace-stopped tracee were both still alive.

**Root cause, evidence-chained:**

1. `Session::terminateDebuggee` (`Source/debug/Session_mac.cpp:352`) calls
   `process.Signal (SIGKILL)`. For a debuggee currently stopped at an *unhandled hardware
   exception* (`eStateCrashed`, `EXC_BAD_ACCESS`), this call fails outright
   (`SBError::Fail() == true`, message `"failed to send signal 9"`) — LLDB's gdb-remote signal
   -injection path cannot deliver an out-of-band signal while the thread is parked mid an
   unresolved Mach-exception reply. This failure was previously swallowed (logged under
   `JUCE_DEBUG` only, no fallback).
2. The pre-fix code called `resume()` (`process.Continue()`) unconditionally regardless of the
   `Signal()` failure. `Continue()` on a crashed thread re-delivers the *same* unhandled
   exception (LLDB's default signal-disposition tables stop-and-notify on `EXC_BAD_ACCESS`
   rather than letting it kill the process) — producing the observed infinite re-fault loop
   (`onExceptionStop` fires again, setting `executionState = stopped`).
3. `Whatdbg::onDisconnect` had set `executionState = running` to keep `run()`'s poll gate
   (`if (running or launching) pollEvents()`) active — but the very next re-fault event flips
   `executionState` back to `stopped`, so `pollEvents()` stops being called for the remainder of
   the wait.
4. With polling stalled and the debuggee genuinely still alive, `Whatdbg::drainTerminateTimeout`'s
   5-second deadline force-sets `executionState = exited; isRunning = false` — a lie: the
   debuggee never actually died.
5. `getEndModeForExit()` reads the forced `exited` state and returns `EndMode::passive`, so
   `Session::shutdown` runs its `passive` branch (no-op) and immediately tears down the
   `SBDebugger` (and its `debugserver` connection) while the debuggee is still alive and
   ptrace-stopped — the exact tracer-abandonment mechanism documented in
   `RFC-ZOMBIE-TERMINATION.md`, here reached through the exception-loop/deadline path rather
   than an immediate `Destroy()`.
6. `debugserver`, orphaned when `whatdbg` exits, is later reaped or exits itself, and the
   never-resumed, never-killed `fixture_crash` reparents a second time to `launchd`, which (this
   machine's already-documented reaping defect) never collects it — permanent `PPID=1` zombie.

## Fix

`Source/debug/Session_mac.cpp:352-368` — `Session::terminateDebuggee`: on `Signal (SIGKILL)`
failure, fall back to `process.Kill ()` (an existing `SBProcess` member, already named in the
task's own citation of the RFC's Option B) instead of blindly calling `resume ()`, which only
ever re-delivered the same unhandled exception. `Kill()` is LLDB's dedicated "make the process
die regardless of current exception/signal state" operation and, called here while `run()`'s
poll loop is still actively pumping (unlike the previously-fixed `EndMode::terminate` shutdown
path, which ran *after* the loop stopped), resolves without blocking the adapter. On the
existing success path (a plain breakpoint/thread-started stop, `Signal()` succeeds), behavior is
unchanged — `resume()` still runs exactly as before.

```cpp
void Session::terminateDebuggee (std::uint32_t processId) noexcept
{
    juce::ignoreUnused (processId);
    const lldb::SBError error { process.Signal (SIGKILL) };

    if (error.Fail ())
    {
#if JUCE_DEBUG
        jam::debug::Log::write (juce::String ("[Session_mac] terminateDebuggee failed: ")
                                 + error.GetCString ());
#endif
        juce::ignoreUnused (process.Kill ());
    }
    else
    {
        resume ();
    }
}
```

No new identifiers introduced — `process.Kill ()` is the existing `SBProcess` member already
cited in the task prompt and already declared in the vendored `SBProcess.h` header
(`Resources/macos/include/lldb/API/SBProcess.h:166`).

Post-fix verification (3 isolated `08_crash` repro runs): zombie count identical before/after on
all three runs, `Kill()` reported success on every run, no leftover `whatdbg`/`debugserver`/
`fixture_crash` process after any run.

`Source/debug/Session_mac.cpp`'s `EndMode::detach` branch (`process.Detach ()`) and the harness's
`02_attach`/`10_disconnect_detach` cleanup code were left untouched — neither is implicated by
the evidence gathered this session (see "Investigation" above; `02_attach` never leaked a zombie
in 4 isolated repro runs, pre- or post-fix).

## Summary

pass=10 fail=0 on all three full runs. Zombie count did not rise across any of the three runs
(net change: 0). Root cause was a whatdbg defect — `Session::terminateDebuggee` had no fallback
when `SBProcess::Signal (SIGKILL)` fails against a debuggee stopped at an unhandled hardware
exception, causing an infinite re-fault loop that the 5-second terminate deadline papered over by
force-declaring the debuggee `exited` and tearing down the debugger connection while it was still
alive and ptrace-stopped — reproducing `RFC-ZOMBIE-TERMINATION.md`'s tracer-abandonment mechanism
via `08_crash`, not `02_attach`. Fixed by falling back to `SBProcess::Kill ()` when `Signal()`
fails. `02_attach` was directly investigated and exonerated by process-table evidence, not
assumption.
