- [info] fix: `Whatdbg::onDisconnect` no longer sets `state.isRunning = false` immediately on a terminate request while the debuggee is alive. It now calls the new `Session::terminateDebuggee (processId)` (non-blocking) and forces `state.executionState = ExecutionState::running` so the main loop keeps calling `session.pollEvents`. On macOS, `Session::terminateDebuggee` calls `SBProcess::Signal (SIGKILL)` followed by `resume()` (`SBProcess::Continue()`) — `Signal` alone queues the kill but does not deliver it while the target is ptrace-stopped at a breakpoint; `Continue()` releases the stop so the queued SIGKILL is actually delivered. The resulting `eStateExited` event flows through the existing `onProcessEvent`/`onProcessExited` path, which sets `hasProcessExited`, `executionState = exited`, and only then `isRunning = false` — the main loop does not exit until the debuggee's exit has actually been observed. `Session::shutdown`'s `EndMode::terminate` case no longer calls the blocking `process.Kill()`; by the time `shutdown()` runs, `executionState` is already `exited`, so `getEndModeForExit()` returns `EndMode::passive` and the switch is a no-op. `lldb::SBDebugger::Terminate()` is unchanged. The `detach` path (`EndMode::detach` → `process.Detach()`) is untouched.
- [info] evidence for the Signal-alone failure: an interim build using only `process.Signal (SIGKILL)` (no `resume()`) was manually verified — the debuggee remained alive (`ps` STAT `SNX`, sleeping + traced) well past the 5s wait window and never exited. The queued SIGKILL was never delivered because the tracee stayed ptrace-stopped. Killing the interim build's stray `whatdbg`/`debugserver` processes by hand released the ptrace stop and let the queued signal take effect, leaving the debuggee's PID as a genuine unreapable zombie (pid 28128, reparented to launchd, still present — see FIX C below). This is exactly the failure mode the RFC names, produced here by the incomplete interim fix, not by the final `Signal` + `resume()` implementation, which produces zero new zombies (verified above).

These processes are still present as of this report. `launchd` (PID 1) is the sole process that can reap them via `wait()`; on this machine it is evidently not doing so promptly for processes reparented to it after their original parent exited. The only observed way to clear them is a reboot, which was not performed per instruction.
