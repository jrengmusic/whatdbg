- [info] **root cause identified by direct process inspection (not a smoke-assertion-only finding):** after `terminate` response is sent, the **whatdbg process itself never exits**. A standalone repro (`initialize` → `launch` → `setBreakpoints` → `configurationDone` → `stopped(breakpoint)` → `terminate`) shows the whatdbg process pinned at 100%+ CPU (`ps` STAT=R, growing CPU time) for 5+ seconds after the terminate response, with the debuggee still alive and unchanged. `Source/debug/Session_mac.cpp:350-367` (`Session::shutdown`) calls `process.Kill()` for `EndMode::terminate` with no listener pump running after the main loop's `while (state.isRunning)` has already exited (`Source/Whatdbg.cpp:64-114`) — `lldb::SBProcess::Kill()` blocks internally waiting for a state-changed event that requires the process's event stream to be serviced, and nothing services it once `Whatdbg::run()`'s polling loop has stopped. whatdbg is left spinning inside `process.Kill()` indefinitely; the debuggee is left ptrace-stopped and alive.
- [info] **secondary confirmation:** when the hung whatdbg process is externally killed (harness cleanup), the previously-ptrace-attached debuggee reparents to launchd (PPID 1) and becomes a genuine unreapable zombie (`STAT=Z`, `<defunct>`) that further `kill -9` cannot remove — this is the exact failure mode named in the RFC ("debuggee becomes an unreapable zombie on macOS terminate"). Four such zombies (pids from this smoke run) remained in the system process table after harness cleanup and could not be reaped by this agent — reaping requires either `launchd` to notice (observed not to happen within several seconds) or a live process calling `waitpid` on them, which no agent-controlled process can do for an already-reparented orphan.
