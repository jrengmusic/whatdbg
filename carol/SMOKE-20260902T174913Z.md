## Runtime fixes (test failures, not compile errors)

**Fix 1 — `Session_mac.cpp::onStopReason` pause-priority regression.** The merged tree
checked the `stopReasons` lookup table before `state.isPausePending`, so a pending pause
that liblldb reports as `eStopReasonBreakpoint` on this build was misclassified as a
breakpoint stop instead of a pause — this exact behavior was already fixed and verified in
`SMOKE-20260902T162205Z.md` (04_pause) before the sweep. Restored `isPausePending` as the
first check, table lookup second, matching the previously-verified fix.

**Fix 2 — `tests/smoke/fixture.cpp` scenario-10 timing.** `10_disconnect_detach` asserts the
debuggee is still alive 500 ms after a non-terminating `disconnect`. The unmodified fixture
resumes from the breakpoint line straight into its final `printf` and `return 0` — sub-
millisecond — so the process legitimately exits before the check runs, indistinguishable from
being killed. Added a named `postBreakpointDelayMs` (1500 ms) `std::this_thread::sleep_for`
after the crash-check block (never reached in the crash path, so `08_crash` timing is
unaffected) — gives the disconnect check a real window to observe the process still running.

**Fix 3 — `Session_mac.cpp::shutdown`, `EndMode::terminate`.** See verification below.

## Session::shutdown EndMode::terminate — regression check (Step 3)

The concern: `shutdown()` calls a blocking `process.Kill()` for `EndMode::terminate` after
`run()`'s poll loop has already exited (nothing left pumping `SBListener`), which hung
indefinitely once before (`SPRINT-LOG` Problem 1, `SMOKE` history). The stated argument —
`Session::terminateDebuggee` already kills the debuggee earlier, so `shutdown()` should only
ever meet an already-exited process — is not always true: `Whatdbg`'s `terminateDeadlineMs`
(`Whatdbg.h`, 5000 ms) can force `state.isRunning = false` before the debuggee's `exited`
event is ever observed, leaving `executionState` at `running` (not `exited`). In that case
`getEndModeForExit()` still returns `EndMode::terminate`, and the old blocking `process.Kill()`
would run into the exact no-event-pump hang on a debuggee that may still be alive.

Reproduced the blocking-`Kill()` hang directly: an ad hoc timing script (unrelated to
`tests/smoke/`, run from scratch space) that sent `terminate`, waited for the response, then
polled `ps` for whatdbg's own pid *without* first closing the client's stdin pipe — with the
pre-fix `process.Kill()`, the adapter process itself stayed alive 60+ seconds (i.e. still
running when the poll timed out). Note: whatdbg's `Reader` thread blocks on stdin until EOF,
so any client that holds the pipe open — by design or, as in this probe, by omission — delays
process exit regardless of `shutdown()`; this is not itself a bug, but it means `shutdown()`'s
own blocking-`Kill()` risk has to be checked with the client-side pipe correctly closed, which
the 10 smoke scenarios already do via `DapClient:close()`.

Fix: changed `shutdown()`'s `EndMode::terminate` case from `process.Kill()` (blocking, waits
for the exit event) to `process.Signal (SIGKILL)` + `resume()` — the identical non-blocking
pair already used by `Session::terminateDebuggee`, which queues the kill and releases any
ptrace stop without waiting for `eStateExited` to be observed.

**Verification, with the client closing its stdin pipe immediately after the `terminate`
response (matching real client behavior and the smoke harness):**

- Run 1: `elapsedMs after close() = 1521.69`
- Run 2: `elapsedMs after close() = 1512.76`
- Run 3: `elapsedMs after close() = 1520.52`

All three runs: whatdbg's own process pid confirmed gone (`exited=true`) well under 2 seconds.
`10_disconnect_detach` (no `Kill()` call at all — pure detach) also passes with no hang. No
run left a whatdbg or fixture process alive; `ps` confirmed after every run.
